The approval binding

"Approved" and "approved this" are different claims. A case can be approved, re-priced when a technician supplies the missing invoice, and then submitted — and the approval a reader sees in the log would be an approval of a different amount. So an approval records the case and the case version, and a submission is valid only against an approval for its own version. An approval recorded after a submission does not count: counting it would let a system submit first and paper over it afterwards, which is the failure a four-eyes control exists to prevent.

Approvals from this console

There is exactly one route in this console that mutates anything — POST /api/case/{claim_id}/approval — and three things have to be true before it records an event: the deployment must not be read-only, an approver token must be configured, and the caller must present it in the {{ approver_header }} header. WCR_READ_ONLY defaults to true and {{ approver_env }} has no default, so an instance that configured neither has both locks. All three refusals are 403.

Events granted here live in this process's memory and are not presented as durable. The durable approval binding is the case machine's checkpoint; this log exists to make the contract visible — that a granted approval names a case and a case version before anything could act on it — and kill condition D is graded from the audit stream rather than from this table.
